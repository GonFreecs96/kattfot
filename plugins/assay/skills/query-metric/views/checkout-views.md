# Checkout views — data dictionary

Two views, one stage ladder. `cart_checkout_session_spine.sql` is the instance
grain; `cart_checkout_funnel_weekly.sql` aggregates it. The second is built on the
first, so they cannot drift apart in the way two independently-written views would.

## Stage ladder

| # | Stage | Spine flag | Weekly count | Settle lag (illustrative) |
|---|---|---|---|---|
| 1 | Cart Created | `cart_created_flag` | `carts_created` | 0d (the open anchor) |
| 2 | Checkout Started | `checkout_started_flag` | `checkouts_started` | 0d |
| 3 | Payment Submitted | `payment_submitted_flag` | `payments_submitted` | 1d |
| 4 | Payment Decisioned | `payment_decisioned_flag` | `payments_decisioned` | 2d (12d for `bank_transfer_review`) |
| 5 | Order Confirmed | `order_confirmed_flag` | `orders_confirmed` | 3d |
| 6 | Shipped | `shipped_flag` | `orders_shipped` | 7d |
| 7 | Delivered | `delivered_flag` | `orders_delivered` | 14d |
| 8 | Return Window Complete | `return_window_complete_flag` | `return_windows_complete` | 44d |

Lags come from `config/checkout-funnel-spec.yaml`. **They are hand-authored and
illustrative, not measured** — the spec says so in machine-readable form
(`illustrative: true`, `calibrated_at: null`) and the test suite holds those flags in
place. In a real deployment the block is generated by measuring open-anchored settle
time on the spine.

## Off-ladder flags

| Flag | Weekly count | What it captures |
|---|---|---|
| `payment_approved_flag` | `payments_approved` | Decision was yes |
| `payment_declined_flag` | `payments_declined` | Decision was no |
| `fraud_failed_flag` | `fraud_failed` | Stopped **before** any decision |
| `returned_flag` | `orders_returned` | A return was initiated inside the window |
| `cart_stale_flag` | `carts_stale` | No progress, past the 30-day convention |
| — | `orders_confirmed_not_shipped` | Confirmed and **still** not shipped (an absence) |

## The three populations people conflate

The most important thing this dictionary documents. Of the payments submitted:

```
payments_submitted
├── payments_decisioned ──┬── payments_approved
│                         └── payments_declined
├── fraud_failed                (never reached a decision)
└── (residual)                  unresolved in a review queue
```

So:

- `payment_approval_rate` is over **decisioned**, not submitted. Defining it over
  submitted folds a review-queue backlog into the approval rate, making an
  operations problem look like a risk-engine problem.
- `payment_submit_to_decision_rate` is a separate metric because the shortfall has
  two causes with two different owners.
- `fraud_check_failure_rate` is over **submitted**, because that is the population
  the check is applied to. Its numerator is absent from the decisioned denominator.

Adding approval rate and fraud rate together describes nothing: they have different
denominators.

## Terminal branches

Deepest-first, so each cart lands in exactly one. This is the drop-off
decomposition: of all carts created, the share that *ended* in each branch.

| Branch | Meaning |
|---|---|
| `8 Return Window Complete` | Delivered, window closed, kept |
| `7r Delivered then Returned` | Delivered, return initiated |
| `7 Delivered (Return Window Open)` | Delivered, still unsettled |
| `6 Shipped (In Transit)` | Dispatched, not yet delivered |
| `5x Cancelled after Confirmation` | Resolved: cancelled |
| `5 Confirmed not Shipped (Out of Stock)` | Stuck: paid, not dispatched |
| `4d Payment Declined` | Decision was no |
| `4f Fraud / Identity Check Failed` | Stopped before a decision |
| `3r Payment Under Review (Unresolved)` | In a queue, may never resolve |
| `3z Stale (Post-Submit)` | Submitted, undecided, aged out |
| `3 Payment Submitted, Undecided` | Recent, still plausible |
| `2 Checkout Started, No Payment` | Entered checkout, did not pay |
| `1z Stale (Pre-Checkout)` | Never entered checkout, aged out |
| `1 Cart Abandoned` | Never entered checkout, still recent |

Note the pairs that differ only by age (`3` vs `3z`, `1` vs `1z`). That distinction
is the difference between "still in flight" and "dead", and it is why the stale lag
is exactly the 30-day abandonment convention: the flag cannot fire sooner.

## Cohort semantics

`cohort_week` is the ISO-Monday week the **cart was created**, kept forever. A cart
created in week *W* that confirms three weeks later still counts in *W*.

Consequences worth stating, because both get rediscovered painfully:

1. **Weekly conversion is comparable.** Activity-time bucketing would attribute an
   outcome to a week whose traffic did not produce it.
2. **Recent cohorts are genuinely incomplete**, not merely noisy. Their deep stages
   have not happened yet, and no query will find them. That is what the per-stage
   maturity cutoffs exist for.

## Per-stage maturity, in one paragraph

A cohort is mature for a (cohort × stage) **pair**. Week *W* has settled its
cart-to-checkout outcome within minutes and its return-window outcome only after
about 44 days. Gating the whole funnel on the slowest stage would throw away six
weeks of perfectly readable early-funnel data; gating on the fastest would report
return rates that are simply not in yet. Each stage is therefore capped at the cohort
weeks mature *for that stage*, via `cohort_week <= @maturity_cutoff`.

The one place this asymmetry bites hardest: a **return** is visible as soon as it is
initiated, part-way through the window, while a **keep** is only confirmed once the
window shuts. So a partially-mature cohort has visible returns and invisible keeps —
biased downward on the kept rate, and biased downward on the return rate too (fewer
returns have accumulated). The second is the flattering direction and therefore the
more dangerous one to read carelessly.

## Offline path

The offline engine does **not** run this DDL. `scripts/generate_fixtures.py` emits
the two views' contents directly as CSVs, and the sqlite adapter loads them. That is
a deliberate scope line: reproducing these `CREATE VIEW` statements offline would
mean shipping a synthetic source-event stream as well, which triples the fixture
surface to test SQL that the BigQuery path already documents.

What the offline path *does* exercise is every metric's own generated SQL — the
`SAFE_DIVIDE`/`SUM`/`GROUP BY` that `assay_query.py` builds — translated once by
`_shared/dialect.py`. So the query construction is genuinely tested; the view
construction is documented and reviewed rather than executed.

## Project substitution

Both files use `${WAREHOUSE_PROJECT}` and `${SOURCE_DATASET}` placeholders. There is
no real project id anywhere in this repository, deliberately: a template that shipped
one would ship somebody else's billing account. The metric definitions use the same
convention (`source_project: ${ASSAY_BIGQUERY_PROJECT}`), expanded from the
environment at query time.
