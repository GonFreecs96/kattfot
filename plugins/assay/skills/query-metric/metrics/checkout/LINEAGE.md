# Checkout module — lineage and shared business rules

No `name:` in frontmatter, so this file is documentation: the metric resolver and
the catalog linter both skip it. It exists because fifteen metric definitions
would otherwise repeat the same six paragraphs, and a rule restated fifteen times
is a rule that will eventually be restated inconsistently.

## Lineage

```
  source events (out of scope for this template)
        |
        v
  analytics.cart_checkout_session_spine      <- session grain, one row per cart
        |                                        stage flags + timestamps +
        |                                        terminal_branch
        v
  analytics.cart_checkout_funnel_weekly      <- pre-aggregated, cohort_week x
                                                channel x payment_method x
                                                market x category x
                                                checkout_version
```

Both are defined in `../../views/`. The weekly aggregate is what every metric in
this directory reads; the session spine is what the spine-backed skills read.
They are two projections of the same stage ladder, and keeping them consistent is
a maintenance obligation, not an accident — `views/checkout-views.md` is the data
dictionary that documents the correspondence.

### Why two views and not one

Because they answer structurally different questions. A ratio metric wants
pre-summed counts at a governed grain: it is cheap, cacheable, and impossible to
accidentally reach individual rows through. Drop-off attribution and percentile
timing want one row per instance, because "where did each cart end up" and "what
was the 90th-percentile time to ship" cannot be recovered from sums.

The weekly view is therefore not a performance optimisation on top of the spine —
it is a **narrower interface**, deliberately. R5 (no individual-level data) is
easier to honour when the governed surface has no individuals on it.

### Why the two views' allow-lists differ

The weekly aggregate is cut by five dimensions; the funnel spec allows six. The
extra one is `is_first_order`, which exists on the session spine but is not carried
into the weekly aggregate: including it would double the cell count and halve the
volume behind every rate, for a slice that matters to fulfilment analysis but not
to any registered ratio. If a metric needs it, add it to the aggregate — do not
widen the metric's allow-list to a column the view does not have.

## Shared business rules

Referenced by id from individual metrics' `business_rules:` frontmatter.

### `cohort_vs_activity_time`

`cohort_week` is the ISO week the **cart was created**, and a cart keeps that
cohort forever. A cart created in week *W* that confirms three weeks later still
counts in *W*.

This is what makes weekly conversion comparable at all — activity-time bucketing
would attribute an outcome to a week whose traffic did not produce it. It is also
what makes recent cohorts genuinely incomplete rather than merely noisy, which
leads directly to the next rule.

### `per_stage_maturity`

A cohort is mature for a **(cohort × stage) pair**, not for itself. A week that has
settled its cart-to-checkout-start outcome (minutes) must not be withheld for the
six weeks a return-window outcome needs.

Each metric declares `maturity_stage:`; the settle lag for that stage lives in
`config/checkout-funnel-spec.yaml`'s `stage_maturity.lag_days` table, and the query
layer applies `cohort_week <= @maturity_cutoff` accordingly. So the same view
serves an early-funnel metric at last week's freshness and a return-window metric
at six weeks' lag, without either lying.

**The lags in this template are hand-authored and illustrative, not measured.**
The spec says so in machine-readable form (`illustrative: true`,
`calibrated_at: null`) and every artifact repeats it. In a real deployment that
block is generated by measuring open-anchored settle time on the spine; a
hand-picked lag is an assumption wearing a measurement's clothes, and the whole
value of the mechanism is that the number was observed.

### `decision_is_not_approval`

Three states get collapsed into "declined" and should not be:

- **Decisioned** — an answer arrived, yes or no.
- **Fraud / identity check failed** — stopped before any decision. In
  `payments_submitted`, absent from `payments_decisioned`.
- **Unresolved review** — sitting in a queue, possibly forever. Also in submitted,
  absent from decisioned.

So `payment_approval_rate` is defined against `payments_decisioned`, and
`payment_submit_to_decision_rate` is a separate metric. Reporting approval as
`approved / submitted` blames the risk engine for the review queue's backlog.

### `return_window_is_thirty_days`

A delivered order is not a settled order. The customer has 30 days from delivery
to send it back, so "kept" is unknowable until the window closes — and because the
window starts at *delivery*, a slow market's orders settle later than a fast
market's for reasons that have nothing to do with conversion.

This is the structural reason the maturity machinery in this template is not
ornamental. Read a recent cohort's `delivered_to_return_window_complete_rate`
without a cutoff and you will get a number near zero, correctly, and misread it as
a collapse in customer satisfaction.

### `confirmation_creates_the_order`

`order_id` is NULL on every session that never confirmed. Orders therefore cannot
be the funnel denominator: an order-grain funnel is structurally blind to the
abandoned cart, which is the largest exit in this ladder. Every end-to-end metric
here is a share of `carts_created`.

### `mix_confounds_unsliced_trends`

`channel` and `category` both move conversion substantially, so an un-sliced trend
partly measures the mix rather than performance. A push into a low-intent channel
lowers the blended rate even when every individual channel improved.

Metrics whose blended value is mix-sensitive say so in their own caveats. The
funnel pulse monitors per-channel for the same reason: holding the mix constant is
the only way a monitor cannot be fooled by it.

### `fixture_data_is_synthetic`

In this template every number comes from `scripts/generate_fixtures.py` — a seeded
random process, not a business. Fixture-backed runs set `fixture_backed: true`,
which watermarks every downstream chart, dashboard, and PDF. Treat the *shape* as
illustrative and the *values* as meaningless.
